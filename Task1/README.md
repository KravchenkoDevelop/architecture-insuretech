# InsureTech — Технологическая архитектура TO-BE

## Контекст задачи

Компания планирует региональную экспансию по всей территории РФ. Требования:
- Доступность **99,9%** (не более ~8,7 часов простоя в год)
- **RTO — 45 минут**, **RPO — 15 минут**
- Обслуживание клиентов из всех часовых поясов (24/7)
- Одинаковое время загрузки страниц независимо от региона пользователя
- Текущий объём данных: **50 GB**

---

## Ход мысли при проектировании

### 1. Масштабирование: горизонтальное vs вертикальное

Вертикальное масштабирование (увеличение мощности одного сервера) быстро упирается в потолок и создаёт единую точку отказа — при падении сервера весь сервис недоступен. Для требования 99,9% этот подход не подходит.

**Выбор: горизонтальное масштабирование** с автоскейлингом (Horizontal Pod Autoscaler в Kubernetes). Новые экземпляры приложения добавляются автоматически под нагрузку, а при отказе отдельного узла трафик перераспределяется на оставшиеся.

Для базы данных при объёме 50 GB вертикальное масштабирование допустимо — данные помещаются на одном мощном узле. Но для отказоустойчивости всё равно нужна репликация.

---

### 2. Мультирегиональность и зоны доступности

Чтобы закрыть требование к обслуживанию всех часовых поясов и одинаковому времени загрузки, система должна физически присутствовать в нескольких регионах РФ. Выбраны **два основных региона** — Москва (первичный) и Екатеринбург (вторичный). Они охватывают европейскую часть и Урал, с возможностью горизонтального расширения на Владивосток и Сибирь по той же схеме.

Внутри каждого региона приложение разворачивается в **двух зонах доступности (AZ)**. Это защищает от отказа целого датацентра — событие, которое реалистично происходит при авариях питания, пожарах и т.д.

---

### 3. Конфигурация Kubernetes: независимые кластеры vs растянутый

Рассматривались два варианта:

**Вариант A: Один растянутый (federated) кластер** через несколько AZ и регионов.
- Единое управление
- Но: высокая латентность между регионами ломает консенсус etcd, сложно обеспечить изоляцию отказов, vendor lock на конкретную реализацию federation.

**Вариант B: Независимые кластеры в каждой AZ** ← **выбранный подход**
- Каждый кластер полностью независим: падение одного не влияет на другие
- Низкая латентность внутри кластера (все узлы в одной AZ)
- Простое управление lifecycle каждого кластера
- Соответствует best practices Yandex Cloud Managed Kubernetes

Итого: **4 независимых кластера** — по 2 в каждом регионе (по одному на AZ).

---

### 4. Балансировка нагрузки: три уровня

Для равномерного распределения трафика и геолокации применяется трёхуровневая схема:

```
Пользователь
    ↓
CDN (PoP в ближайшем городе) ← статика отдаётся локально
    ↓
Глобальный L4 балансировщик (GLB) ← геолокация, выбор региона
    ↓
Региональный L4 LB ← распределение между AZ внутри региона
    ↓
K8s Service (ClusterIP / NodePort) ← балансировка между Pod-ами
```

**Health Checks** на каждом уровне:
- **GLB → региональный LB**: TCP:443 (каждые 5 сек), HTTP GET /health (каждые 10 сек)
- **Региональный LB → K8s кластер**: TCP:8080 + HTTP:8080/health
- **K8s liveness/readiness probes**: HTTP:8080/health (интервал 10 сек, timeout 3 сек)
- Порог вывода из ротации: **2 последовательных неудачи**
- Порог возврата в ротацию: **3 последовательных успеха**

---

### 5. Failover-стратегия

Стратегия строится по принципу **активный-активный** между кластерами внутри региона и **активный-пассивный (warm standby)** между регионами.

| Уровень отказа | Реакция | Время восстановления |
|---|---|---|
| Pod | K8s перезапускает автоматически | секунды |
| Node | K8s мигрирует Pod-ы на другие ноды | 10–30 сек |
| AZ | GLB/LB переключает трафик на другую AZ | секунды |
| Регион | GLB переводит трафик на второй регион | 1–5 мин |
| DB Primary | Промоушен Standby → Primary | до 45 мин (в рамках RTO) |

Второй регион (Екатеринбург) находится в режиме **warm standby**: приложение запущено, БД реплицируется, но основной трафик туда не идёт. При отказе Москвы GLB через DNS failover переводит трафик за ~2–5 минут.

### 6. Конфигурация базы данных

**Почему не шардирование по умолчанию?**
При объёме 50 GB шардирование избыточно — PostgreSQL уверенно справляется с таким объёмом на одном узле. Шардирование добавляет сложность (распределённые транзакции, сложные JOIN-ы, operational overhead) без реальной выгоды на этом масштабе.

**Выбранная конфигурация:**

```
Москва:
  PostgreSQL Primary (Master)
      ↕ синхронная репликация (RPO = 0 внутри региона)
  PostgreSQL Standby (Hot Replica)
      ↓ резервное копирование каждые 5 мин → Object Storage

Москва → Екатеринбург:
  Асинхронная потоковая репликация
  Задержка: 5–10 сек → RPO = 15 мин (с запасом)

Екатеринбург:
  PostgreSQL Secondary (Read Replica)
      + Offline Backup (холодная копия)
```

**Резервное копирование:**
- Полный бэкап: раз в сутки → Yandex Object Storage
- Инкрементальный WAL-архив: каждые 5 минут
- PITR (Point-in-Time Recovery): окно 7 дней
- Это обеспечивает RPO = 15 минут и RTO = 45 минут

**Шардирование — отложенное решение:**
Логическое разделение данных по `region_id` заложено в схему БД как подготовка к будущему горизонтальному масштабированию, если объём данных вырастет в 10x+. До тех пор физического шардирования нет.

---

### 7. Одинаковое время загрузки для всех регионов

Задача решается через CDN (Content Delivery Network):
- Статические ресурсы (JS, CSS, изображения, документы) кешируются на **PoP-серверах** CDN в ближайших к пользователю городах
- Динамические запросы (API) маршрутизируются через GLB к ближайшему региональному кластеру
- TTL кеша настраивается под каждый тип ресурса

Результат: пользователь во Владивостоке получает статику с местного PoP, а API-запросы уходят в ближайший активный кластер — задержка сопоставима с пользователем из Москвы.

## Итоговые характеристики решения

| Метрика | Требование | Решение |
|---|---|---|
| Доступность | 99,9% | Multi-region + Multi-AZ + Auto-failover |
| RTO | 45 мин | Warm standby + автоматический DNS failover |
| RPO | 15 мин | Асинхронная репликация + WAL-архив каждые 5 мин |
| Время загрузки | Одинаковое | CDN PoPs + геолокационный GLB |
| Масштабирование | Рост регионов | Horizontal Pod Autoscaler + добавление регионов |
